01 — Problem & scope

AI-drafted patterns don't learn from being wrong

An AI drafting a bodice has no embodied feedback — it has never worn a garment, so it cannot know a dart pulls or an armhole binds without a human saying so after a physical fitting. It can also be confidently, internally-consistently wrong: this project's own Phase 2 armhole curve passed every automated relationship check (front longer than back, areas, closure) while its control-point bulge was roughly thirty times larger than a real armhole's deviation. And without deliberate memory, every drafting call starts from zero — the same correction gets made, and the same class of error gets re-committed, every time a new pattern is drafted from scratch.

Pattern Tracker's actual point is closing that third gap: a structured body-fit profile and a reference sloper — a bodice version explicitly marked, once it's fitted, as the trusted block — so later bodice-derived drafts start from proven geometry for this body instead of generic formulas re-run from zero. Real patternmaking practice ("draft from a block," not from scratch each time), not a bigger prompt. The revision history (every edit as a structured diff plus the reason) is what makes a sloper trustworthy and what the profile is built from — necessary plumbing underneath the point, not the point on its own.

Scope is deliberately narrow: one user, one body, no accounts, no sharing. That constraint isn't a shortcut — it's what makes SQLite over Postgres, brute-force cosine over a vector database, and a locally-run tool over a hosted one all the correct call rather than the cheap one. At this scale, the simpler option is also the more correct option.

02 — System design

Two pipelines, one data model

The tracker isn't bolted onto a separate drafting tool — it's version 1 onward of whatever the croquis step produced. Draft turns measurements into a structured pattern; track diffs every later edit against the version before it, classifies the kind of change, and logs it with your reasoning. Both read and write the same Pattern model.

The model's one hard rule: geometry is named points, never a raw SVG path string. Every point gets a stable, permanent id, and edges, darts, notches, and grainlines reference those ids rather than positions. A diff between two path strings is meaningless; a diff between two named points by id is exact.

Snapshots and diffs are also kept apart from the reasoning text on purpose. pattern_versions holds a full geometry snapshot per version, so any version re-exports to PDF without replaying history. revisions holds the structured deltas separately. Only Revision.embedding_text() — a sentence built from those deltas — gets embedded for the future RAG layer to search. Retrieval can describe a change; it can never originate a measurement, because the number always comes from deltas, read directly.

03 — Stack & decisions

Choices made ahead of the pressure to reverse them

  • Pydantic dataclasses, not BaseModel. Porting the schema to Pydantic (Phase 1) needed real validation without breaking the positional construction already used throughout the codebase — Point("a", 0, 0), not Point(id="a", x=0, y=0). pydantic.dataclasses.dataclass gives full validation and coercion while keeping dataclass-style __init__ and __post_init__ — verified empirically before committing, rather than assumed.
  • No vector database. Revision embeddings will be float32 BLOBs in SQLite, searched by brute-force cosine in Python (Phase 6, not built yet). One user, low hundreds of revisions — a linear scan over a few hundred rows beats the import cost of a vector-DB client. Decided up front so Phase 6 doesn't re-litigate it under time pressure.
  • Seam allowance is one float, not baked-in geometry. Stored geometry is always the stitching line. The cut line is computed at export time by offsetting outward — so changing the seam allowance is a one-field revision, not a change to every coordinate in the piece.
  • Every version is a full snapshot. Revisions are derived, never authoritative. This costs some storage at personal scale and buys back the ability to re-export any past version without replaying its whole history.
04 — Build, phase by phase

What actually shipped

0

Repo setup 1 test

uv-managed project on a hatchling build backend rather than uv_build's default — the repo's flat api/ package layout needed explicit package discovery to install editable and resolve from tests, scripts, and uvicorn alike regardless of working directory. .env for the Anthropic key, gitignored; api/db.py runs the DDL on every connection (idempotent — every statement is CREATE TABLE IF NOT EXISTS).

1

Harden the schema 16 tests

Diff tests were written first, against the then-unmodified schema, specifically to find gaps rather than assume the schema was already correct.

Bug found by the tests, not inspection

Segment was the only schema object with no stable id. A bezier control-point change fell back to a whole-list comparison instead of a precise delta — the test asserting a one-field diff failed against real output. Fix: a derived id, f"{start}->{end}", placed last in the field list to keep every existing positional call site working unchanged.

Also added infer_change_type(deltas), priority-ordered so a revision that moves a dart and nudges seam allowance in the same edit reads as DART — the dominant, structural change — not SEAM_ALLOWANCE.

2

Drafting engine 7 tests

A fitted bodice block, front and back, following Winifred Aldrich's Metric Pattern Cutting for construction order — armhole depth and width from the bust measurement, shared neck width with the front dropped lower, a sloped shoulder, a bust dart, waist suppression split across the side seam and darts.

Confidence, stated plainly

The construction order is confident. The numeric constants — the armhole-depth add-on, the neck-width fraction, the suppression split — are reconstructed from general metric-drafting practice, not transcribed from the text. Two of them (back_width, neck_circumference) now use a real measurement when supplied instead of a bust-derived guess. Tests check relationships (front armhole longer than back, waist width exactly equals waist-plus-ease-minus-darts) rather than absolute values — deliberately, since the absolute values aren't verified against the book or a muslin.

3

SVG & PDF export 22 tests

Bezier curves flatten to a polyline before anything else happens to them — offsetting a cubic bezier exactly has no closed form, so the seam allowance is a per-vertex mitred offset of the flattened outline, same approach for both the SVG preview and the tiled PDF.

Bug found by the tests, not inspection

The first offset implementation shrank each piece inward instead of expanding it outward — a sign error in which side of the outline counted as "out". Caught immediately by a test asserting the cut line's area must exceed the stitching line's, before it ever reached the SVG or PDF layer.

The PDF tiles across Letter or A4 with a repeating registration-mark grid for alignment and a mandatory 50mm calibration square. Page 1 is a scaled-down assembly overview with a numbered grid showing which tile is which page — the square stays at true scale in the corner, separate from the scaled-down view around it, so "page 1 has a real 50mm square" stays literally true. The physical ruler check on a real printout hasn't been reported back yet — print scale is unverified until it is.

06 — What it can't do

Said plainly, not buried in a footnote

  • Drafting is a first draft, never a fitted pattern — the construction constants are reconstructed, not verified against the text or a muslin.
  • Outline reconstruction assumes one simple closed loop per piece (every point has exactly two connections). True for the bodice today; branching geometry isn't handled.
  • Darts are drawn as surface annotations, not cut as a V into the outline — the simpler of two real conventions, chosen without strong confidence it's the more common one.
  • Print scale is unverified until the physical ruler check on the calibration square is reported back.
  • No garment type beyond a bodice block yet — skirt/trouser/sleeve measurements already exist on the schema, deliberately ahead of need, but no drafting logic uses them.
07 — Deployment & next

Local only, on purpose

This runs on one machine, never deployed live. A public deployment means an Anthropic API key and a vision/RAG endpoint anyone could hit — rate limiting, auth, and spend caps just to stay safe — and it would put body measurements and fit notes on a public host for no real benefit: a visitor has no croquis and no muslin, so a live version would show them an empty tool. The revision history that's the actual point of the project only accumulates through real sewing, which only happens here.

The portfolio's sewing-box item links to a case study about this project instead of an embedded feature — that write-up lives at docs/CASE_STUDY.md in this repo, updated phase by phase alongside this log. Next up: Phase 4 (croquis interpretation) or Phase 5 (revision API), independent of each other once Phase 2 landed — both feed Phase 6, where the body profile and reference sloper actually close the loop described in §01.
